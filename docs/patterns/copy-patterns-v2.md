> ✅ **글자수 기준 확정 (2026-08-06)**: 초안에 서브타이틀 14자/메인타이틀 17자로
> 잘못 적혀 있었다. 공식 기준은 [copy-patterns.md](copy-patterns.md)와
> [kakaopay-banner-guide.md](../guides/kakaopay-banner-guide.md)와 동일하게
> **서브타이틀 15자 / 메인타이틀 14자**다. 아래 본문 전체를 이 기준으로 수정했다.

> v1([copy-patterns.md](copy-patterns.md))과의 핵심 차이: 카테고리를 사용자에게
> 다시 묻지 않고 오브젝트 선택(1단계)에서 자동 도출한다. 혜택도 자유 텍스트 한
> 줄이 아니라 유형/수치/조건/기한으로 구조화해서 입력받는다.

## 0. 전체 플로우: 오브젝트 선택이 먼저다

실제 플로우는 [오브젝트/이미지 선택] → [혜택 입력] → [문구 3안 생성] 순서다.

이 순서가 핵심인 이유: **오브젝트를 먼저 고른다는 건, 카테고리 정보가 이미 확정된
상태로 문구 생성에 들어간다는 뜻**이다. 그래서 "카테고리를 선택하세요"라고 다시
묻는 건 중복 입력이 된다.

```
[1단계: 오브젝트 선택]          [2단계: 혜택 입력]        [3단계: 문구 3안 생성]
사용자가 3D 에셋 라이브러리      "최대 15% 할인"          object_tag + benefit
에서 오브젝트 선택                                        (+ target, 선택)
(예: 자동차, 커피, 화장품)              ↓                        ↓
        ↓                    벤핏 텍스트만 입력          category는 object_tag에서
object_tag 자동 부여                                      자동 매핑 (재입력 X)
(예: "car", "beverage")
```

**설계 원칙**: object_tag를 category의 대체 입력값으로 사용한다. 즉 사용자 입력
단계는 실질적으로 **오브젝트 선택(이미 함) + 혜택 입력** 두 가지뿐이고, 타겟팅만
선택적으로 추가하면 된다.

### object_tag → category 매핑 테이블 (예시)

| object_tag (에셋 라이브러리) | category (문구 생성용) | 톤 제약 |
|---|---|---|
| car, calculator | 금융/보험 | 확정·보장 표현 금지 |
| coin, chart | 금융/증권 | 확정·보장 표현 금지 |
| shopping_bag, tag | 커머스/쇼핑 | 트렌디 어휘 허용 |
| beverage, dessert | F&B | 감각적 표현 허용 |
| cosmetic, mirror | 뷰티 | 효능 과장 표현 주의 |

이 매핑 테이블은 에셋 라이브러리 태깅 체계와 그대로 연동하면 되니, 별도 DB 없이
기존 에셋 메타데이터를 재사용할 수 있다.

### 추가로 중요한 규칙: 오브젝트-문구 중복 방지

오브젝트가 이미 시각적으로 상황/상품을 보여주고 있기 때문에, 문구에서 같은 정보를
텍스트로 또 반복하면 안 된다.

- 나쁜 예: 자동차 오브젝트 + 서브타이틀 "자동차 보험이 필요할 때" (오브젝트와 중복)
- 좋은 예: 자동차 오브젝트 + 서브타이틀 "엇, 벌써 만기라면" (오브젝트가 보여주는 걸 문구는 보완)

이 규칙은 프롬프트에 명시적으로 넣어야 한다 (3번 항목 참고).

## 1. 입력값 설계: 왜 3단계로 나누는가

| 입력값 | 출처 | 필수 여부 | 출력 정확도에 미치는 영향 |
|---|---|---|---|
| **object_tag** (오브젝트 태그) | 1단계 오브젝트 선택 시 자동 부여 | 필수 (자동) | category를 대체. 업종별 어휘·규제 반영의 근거가 됨 |
| **혜택** (benefit) | 사용자 직접 입력 | 필수 | 메인/서브타이틀의 '내용'을 결정 |
| **타겟팅** (target) | 사용자 직접 입력 | 선택 | 상황 기반형(패턴1)의 품질을 좌우. 타겟이 없으면 "상황 제시"가 추상적으로 나옴 (예: "돈 걱정될 때" vs 타겟이 "2030 사회초년생"이면 "월급 반, 카드값 반일 때") |

**설계 원칙**: 사용자가 실제로 타이핑하는 건 혜택 하나뿐이다. category는 이미
1단계에서 고른 오브젝트로부터 자동 도출되므로 별도 입력 단계 자체가 사라진다.
타겟팅만 선택적으로 열어두면 된다.

즉 UI 카피로는 이렇게 안내하면 된다:

> "혜택만 입력하면 방금 고른 이미지에 맞는 문구 3안이 생성돼요. 타겟을 추가하면 더 정교해져요."

## 2. 시스템 프롬프트 (1단계: 생성)

```
당신은 성과형 광고 배너 카피라이터입니다.
아래 4가지 검증된 패턴에 따라, 입력된 정보를 기반으로 배너 문구를 생성합니다.

# 패턴 정의
1. 상황기반+문제제기 (인지·관심 유도용)
   - 서브타이틀: 사용자 상황을 구체적으로 제시 (타겟이 공감할 만한 현실적 장면)
   - 메인타이틀: 문제를 제기하며 행동을 유도 (질문형 또는 자각 유도형)
2. 혜택조건+결과형(보상) (신뢰·구체성 강조용)
   - 서브타이틀: 혜택을 받기 위한 조건을 명시 (숫자·기간·자격 등 구체적으로)
   - 메인타이틀: 조건 충족 시 얻는 최종 혜택/보상을 강조
3. 혜택+행동유도 CTA형 (전환 유도용)
   - 서브타이틀: 핵심 혜택을 간결하게 제시
   - 메인타이틀: 혜택 확인/탐색을 유도하는 명령형 CTA
4. 조건+혜택강조형 (전환·신뢰 동시 강조용)
   - 서브타이틀: 핵심 혜택을 제시
   - 메인타이틀: 최종 혜택/보상을 임팩트 있게 강조 (숫자 강조 권장)

# 입력 변수
- object_tag (필수, 1단계 오브젝트 선택에서 자동 전달): {object_tag}
- category (필수, object_tag → category 매핑 테이블에서 자동 도출): {category}
- benefit (필수, 사용자 입력): {benefit}
- target (선택, 사용자 입력): {target}

# 작성 규칙
1. 서브타이틀 최대 15자, 메인타이틀 최대 14자 (공백 포함, 카카오페이 핏배너 기준)
2. category가 "금융/증권"이면 확정 수익, 보장, 무조건 등 단정적 표현 금지
3. target이 있으면 패턴1의 서브타이틀에 해당 타겟의 실제 생활 맥락을 반영
4. target이 없으면 패턴1은 category에서 일반적으로 통용되는 상황으로 대체
5. **동일 문구 반복 절대 금지**: 3개 패턴 × (서브타이틀+메인타이틀) 총 6개 필드 중,
   완전히 같은 문장/구절이 두 번 이상 나오면 안 된다(예: "해외주식 수수료 0원"을
   패턴2 메인타이틀과 패턴3 서브타이틀에 동시에 쓰는 것 금지). benefit 값을 그대로
   복사해서 여러 필드에 붙여넣지 말고, 매 필드마다 다른 표현으로 바꿔 쓸 것. 숫자·
   혜택명 같은 핵심 정보는 반복돼도 되지만 앞뒤 문장 전체가 동일해선 안 된다.
6. 느낌표는 패턴3(CTA형)에만 허용, 나머지는 평서형 또는 의문형
7. object_tag가 이미 시각적으로 표현하는 대상(사물명)을 서브/메인타이틀에 그대로 반복하지 말 것
   (예: object_tag가 "car"면 "자동차"라는 단어 자체를 문구에 쓰지 않고, 오브젝트가 암시하는 상황/감정으로 대체)

# 출력 형식 (JSON only, 설명 텍스트 금지)
{
  "recommendations": [
    {
      "pattern": "상황기반+문제제기",
      "subtitle": "",
      "maintitle": "",
      "reason": "이 패턴을 추천한 1줄 근거"
    },
    { "pattern": "혜택조건+결과형", "subtitle": "", "maintitle": "", "reason": "" },
    { "pattern": "혜택+CTA형", "subtitle": "", "maintitle": "", "reason": "" }
  ]
}

주의: 3개 패턴만 출력합니다 (4개 중 입력값과 가장 적합한 3개를 선정).
patttern4는 patttern2와 구조가 유사하므로, benefit이 조건부(예: "~하면 ~%할인")일 때만 patttern2 대신 채택하세요.
```

## 3. 검증(할루시네이션 방지) 프롬프트 - 2단계

카카오페이 GPT-4o-mini 카피 파이프라인에 쓴 것처럼, 여기도 2단계 검증을 넣는 걸
추천한다.

```
아래는 1단계에서 생성된 배너 문구 JSON입니다.
다음 기준으로 각 항목을 검수하고, 위반 시 수정하세요.

# 검수 기준
1. subtitle/maintitle에 입력된 benefit 값에 없는 수치나 조건이 추가되지 않았는가
   (예: 원본 혜택이 "최대 15% 할인"인데 "20% 할인"으로 부풀리지 않았는가)
2. category가 금융/증권일 때 "손실 없이", "무조건", "보장" 등 규제 위반 소지 표현이 없는가
3. 글자 수 제한(서브 15자/메인 14자, 공백 포함)을 초과하지 않았는가
4. 6개 필드(3패턴 × 서브/메인) 중 완전히 동일한 문장/구절이 두 번 이상 등장하지 않는가
   (특히 benefit 값을 그대로 복사-붙여넣기한 필드가 2개 이상 있지 않은지 확인)
5. object_tag가 이미 시각적으로 표현하는 사물명 자체가 subtitle/maintitle에 그대로
   쓰이지 않았는가 (예: object_tag가 "카드"면 "카드"라는 단어 자체를 문구에 쓰지 않았는지 확인)

# 출력
문제 없으면 원본 그대로, 문제 있으면 수정된 JSON만 반환 (설명 금지)

입력: {object_tag, category, benefit, step1_output} — 검증은 반드시 원본 object_tag/
benefit 값을 함께 받아서 대조해야 한다(1단계 출력 JSON만 넘기면 규칙1·5를 실제로
검증할 방법이 없다 — 2026-08-06 실제 구현에서 이 누락으로 "카드" object_tag가
"이 카드로 결제하면" 서브타이틀에 그대로 반복되는 걸 검증 단계가 못 잡은 사례로 확인).
```

## 4. 사용자 입력 UI 문구 제안

```
[1단계: 이미 선택하신 이미지] — 자동 반영, 재입력 불필요
🖼️ (선택한 오브젝트 썸네일) · object_tag: car

[혜택을 입력해주세요] *필수
예: 신규 가입 시 최대 15% 할인

[타겟] (선택 — 입력 시 공감 포인트가 명확해져요)
예: 2030 직장인, 육아맘, 자취생 등 자유 입력 또는 프리셋
```

카테고리 선택 단계 자체를 없앤 것이 포인트다. 사용자 입장에서는 "이미지 고르고
혜택만 쓰면 끝"으로 체감되고, 시스템 내부적으로는 category가 필수값으로 채워져
있는 상태가 된다.

## 5. 정확도 비교 시뮬레이션 (설계 검증용)

| 입력 조합 | 예상 결과물 품질 |
|---|---|
| object_tag + 혜택만 | 패턴2·3은 안정적 / 패턴1은 다소 일반적인 상황 묘사 |
| object_tag + 혜택 + 타겟 | 패턴1의 공감도가 크게 상승, CTR 상관관계가 가장 높을 것으로 예상되는 조합 |
| object_tag ↔ benefit 카테고리 불일치 시 | (예: 오브젝트는 "car"인데 혜택 텍스트가 "적금 이자") → 검증 단계에서 category 재확인 필요, 아래 참고 |

이 표를 근거로 "왜 오브젝트 선택을 카테고리 입력의 대체 수단으로 썼는지"를
설명할 수 있으면, 입력 설계 자체가 UX 의사결정이었다는 스토리가 된다.

### 예외 케이스: object_tag와 benefit이 안 맞을 때

오브젝트는 "car"인데 사용자가 "적금 이자 5%"처럼 다른 업종 혜택을 입력하는
경우가 생길 수 있다. 이건 검증 프롬프트(2단계)에 규칙 하나만 추가하면 된다.

```
5. object_tag가 암시하는 업종과 benefit의 내용이 명백히 다르면,
   category를 benefit 내용 기준으로 재추정하고 그 사실을
   "warning" 필드에 1줄로 남길 것 (예: "오브젝트는 자동차지만 혜택은 예적금 관련입니다")
```

이러면 문구 생성은 막히지 않으면서, 프론트에서 "혹시 다른 오브젝트를
원하셨나요?" 같은 넛지를 띄울 근거 데이터가 생긴다.

## 6. 혜택 입력 구성요소 설계

"카드 + 5000원 할인"처럼 한 줄로 입력하면 혜택의 '크기'만 있고 '조건/대상/기한'이
빠져서, 패턴2(조건+결과형)·패턴4(조건+혜택강조형)가 제대로 힘을 못 쓴다. 아래처럼
4개 구성요소로 나눠서 받는다.

| 구성요소 | 설명 | 필수 여부 | 예시 | 없을 때 생기는 문제 |
|---|---|---|---|---|
| **혜택 유형** | 할인/적립/캐시백/무료배송/수수료면제 중 선택 | 필수 | 즉시할인 | 유형이 없으면 톤을 못 정함 (할인은 임팩트형, 적립은 누적형 어휘가 다름) |
| **혜택 수치** | 숫자+단위 | 필수 | 5,000원 | (이미 있음) |
| **발생 조건** | 이 혜택을 받으려면 뭘 해야 하는지 | 권장 | 신규가입 후 첫 결제 시 | 없으면 패턴2·4가 "조건 제시" 자리를 못 채워서 패턴1·3만 반복 생성됨 |
| **대상/기한** | 누구까지, 언제까지 | 선택 | 이번 달 신규가입자 한정 | 없으면 긴급성·희소성 어휘(마감임박 등)를 못 씀 |

### Before / After 비교

**Before (기존 입력)**
```
오브젝트: 카드
혜택: 5000원 할인
```
→ 조건이 없어서 패턴2 서브타이틀이 "간편 가입만 하면" 같은 일반적 문구로 채워짐
(실제 조건과 무관)

**After (구성요소별 입력)**
```
오브젝트: 카드
혜택 유형: 즉시할인
혜택 수치: 5,000원
발생 조건: 신규가입 후 첫 결제 시
대상/기한: 이번 달 한정
```
→ 이렇게 되면:
- 패턴1 서브타이틀: "카드값 빠듯한 이번 달엔" (대상/기한의 '이번 달'을 상황으로 재활용)
- 패턴2 서브타이틀: "첫 결제만 하면" / 메인타이틀: "5,000원 즉시할인"
- 패턴3 메인타이틀: "이번 달 한정, 지금 받기!" (기한을 CTA 긴급성으로 전환)

같은 5,000원 할인이라도 구성요소가 채워지면 4개 패턴이 서로 다른 근거로 문구를
만들 수 있게 된다.

### UI 설계 제안

혜택을 한 줄 텍스트 입력창 하나로 받지 말고, 아래처럼 짧은 필드 3~4개로 쪼개는
걸 추천한다.

```
[혜택 유형]  드롭다운: 할인 / 적립 / 캐시백 / 무료배송 / 수수료면제
[혜택 수치]  숫자 입력: ___ 원 또는 ___ %
[발생 조건]  (선택) 자유 입력: 예) 첫 결제 시, 3만원 이상 구매 시
[대상/기한]  (선택) 자유 입력: 예) 신규가입자, 이번 달까지
```

필수는 유형+수치 두 개뿐이라 입력 부담은 거의 늘지 않으면서, 조건/기한이
채워질수록 4패턴 전체의 다양성과 구체성이 올라가는 구조다.

## 8. 전체 시스템 구조: 이미지 프롬프트 + 카피 프롬프트

두 프롬프트는 순차 실행되며, 1번의 출력(object_tag)이 2번의 입력값으로 그대로
전달된다.

```
[사용자: 오브젝트 키워드 입력]        [사용자: 혜택 구성요소 입력]
        "카드"                        유형·수치·조건·기한
            │                                 │
            ▼                                 │
   ┌─────────────────┐                        │
   │ ① 이미지 프롬프트  │                        │
   └─────────────────┘                        │
            │                                 │
            ▼                                 ▼
   image asset + object_tag ──────────►  ┌─────────────────┐
                                          │ ② 카피 프롬프트   │
                                          └─────────────────┘
                                                   │
                                                   ▼
                                        문구 추천 3안 (JSON)
```

### ① 이미지 프롬프트 시스템

**목적**: 사용자가 입력한 오브젝트 키워드를 정규화하고, 배너용 이미지(또는 에셋
매칭)와 함께 카피 프롬프트가 쓸 `object_tag`를 만든다.

```
[System Prompt]
당신은 배너 오브젝트 선택기입니다.
사용자가 입력한 키워드를 아래 사전 정의된 object_tag 목록 중
가장 가까운 것으로 매핑하고, 해당하는 이미지 에셋을 반환합니다.

# 입력 변수
- object_keyword (필수, 사용자 입력): {object_keyword}
- style (선택, 배너 무드): {style}

# 규칙
1. object_keyword를 사전 정의 태그(car, card, coin, chart, shopping_bag,
   beverage, cosmetic, gift 등)와 매칭. 정확히 일치하는 게 없으면
   의미상 가장 가까운 태그로 대체 (예: "체크카드" → card)
2. 매칭되는 에셋이 라이브러리에 없으면 fallback_needed: true 반환
3. style이 있으면 해당 톤에 맞는 컬러 tint 적용 (예: "블루톤")

# 출력 형식 (JSON only)
{
  "object_tag": "",
  "asset_id": "",
  "category": "",       // object_tag → category 매핑 테이블 참조
  "fallback_needed": false
}
```

이 단계에서 실시간 생성 대신 **사전 빌드된 3D 에셋 라이브러리에서 매칭**하는
방식(카카오페이 방식과 동일)을 쓰면 속도·비용 면에서 유리하다. object_tag는
자유 텍스트가 아니라 미리 정의된 목록 안에서만 나오게 강제하는 게 중요하다.
그래야 2번 프롬프트의 category 매핑 테이블이 안정적으로 작동한다.

> 2026-08-06: 실제 구현체(`src/lib/asset-library.ts`,
> `src/lib/style2-asset-library.ts`)는 이미 이 방식으로 동작한다 — 다만 지금은
> `object_tag`/`category` 개념이 코드에 명시적으로 노출돼 있지 않고 키워드
> 매칭 → 카테고리(파일 내부에서 style2-design-system.ts의 IconCategory) 순서로
> 암묵적으로만 연결돼 있다. 카피 프롬프트와 연동하려면 이 매핑을 명시적인
> `object_tag`/`category` 응답 필드로 노출하는 작업이 필요하다.

### ② 카피 프롬프트 시스템

**목적**: ①에서 받은 `object_tag`/`category`와 사용자가 입력한 혜택(유형·수치·
조건·기한)을 조합해 3개 패턴 문구를 생성한다. (2번 섹션과 동일, 입력 변수만
아래처럼 정리)

```
# 입력 변수
- object_tag (필수, ①의 출력): {object_tag}
- category (필수, ①의 출력): {category}
- benefit_type (필수, 사용자 입력): {benefit_type}       예) 즉시할인
- benefit_value (필수, 사용자 입력): {benefit_value}     예) 5,000원
- condition (권장, 사용자 입력): {condition}             예) 첫 결제 시
- deadline (선택, 사용자 입력): {deadline}               예) 이번 주까지
- target (선택, 사용자 입력): {target}

# 나머지 규칙·출력 형식은 2번 섹션 시스템 프롬프트와 동일
```

### 왜 두 개로 분리하는가

- **책임 분리**: 이미지 프롬프트는 "무엇을 보여줄지", 카피 프롬프트는 "무엇을
  말할지"만 담당하므로 각각 독립적으로 개선·테스트 가능
- **비용 구조**: 이미지는 에셋 매칭(저비용), 카피는 LLM 생성(상대적 고비용)으로
  성격이 달라 파이프라인을 나눠야 캐싱·재시도 전략을 따로 짤 수 있음
- **오브젝트-혜택 불일치 검증**: object_tag가 먼저 확정된 상태로 카피
  프롬프트에 들어가므로, 5번 섹션에서 다룬 "카드 오브젝트 + 증권 혜택" 같은
  불일치를 카피 프롬프트 단계에서 바로 감지 가능
- **A/B 테스트 설계**: 혜택만 입력 vs 혜택+카테고리+타겟 입력, 두 그룹의 실제
  CTR 차이를 측정하는 실험을 넣으면 "가설 → 검증" 스토리가 완성된다.
- **reason 필드 활용**: 광고주에게 "왜 이 문구가 추천됐는지" 1줄로 보여주면
  신뢰도가 올라가고, 이후 어떤 패턴을 더 많이 선택하는지 로그를 쌓으면 추천
  우선순위 로직 고도화에도 쓸 수 있다.
